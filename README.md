# نظام إدارة العهد النقدية للاتحادات

تطبيق بمعمارية Backend حقيقية: المتصفح **لا يتصل بـ Supabase مباشرة إطلاقًا ولا يعرف عنه أي شيء** (لا رابط ولا مفتاح). كل طلب يمر عبر خادم Node.js/Express (`server.js`) مستضاف على Render، وهو الوحيد الذي يملك بيانات الاتصال بقاعدة البيانات (محفوظة في متغيرات بيئة Render السرّية فقط).

```
المتصفح  →  server.js (Render)  →  Supabase (Postgres)
  (لا يعرف شيئًا عن Supabase)      (يملك مفتاح service_role السرّي)
```

## محتويات المستودع

| الملف | الوصف |
|---|---|
| `login.html` | بوابة الدخول واختيار النظام |
| `index.html` | نظام العهد النقدية — الواجهة فقط، تتحدث مع خادمنا عبر مسار واحد `/api/db` |
| `secondments.html` | نظام الانتدابات وتذاكر السفر |
| `server.js` | الخادم: يستقبل الطلبات من الواجهة، يتحقق من هوية المستخدم وصلاحياته، وينفّذها على Supabase باستخدام مفتاح service_role السرّي |
| `package.json` | تبعيات الخادم (`express`, `compression`, `multer`, `@supabase/supabase-js`) |
| `schema.sql` | مخطط قاعدة البيانات الكامل — يُشغَّل مرة واحدة على مشروع Supabase **جديد** |
| `migration-roles-v3.sql` | ترقية تُشغَّل مرة واحدة على قاعدة بيانات **قائمة بالفعل**: صلاحيتا "رئيس مجلس الادارة" و"مرافق لاعب"، وسؤال الاتحاد القاري، وحقل المهمة/الدور للمشاركين |
| `migration-roles-v4.sql` | ترقية تُشغَّل بعد v3: صلاحية "مدير اللجنة"، وسؤال الاتحاد القاري لأعضاء المجلس، وضوابط سفر مجلس الإدارة |
| `security-migration.sql` | ترقية أمنية تُشغَّل مرة واحدة على قاعدة بيانات **قائمة بالفعل** (تشفير كلمات المرور المخزَّنة كنص صريح) |
| `README.md` | هذا الملف |

## خطوات الإعداد

### 1) إنشاء مشروع Supabase وتشغيل المخطط
1. أنشئ مشروعًا على [supabase.com](https://supabase.com).
2. **SQL Editor → New query** → الصق محتوى `schema.sql` كاملاً → **Run**.
   - هذا الملف أيضًا ينشئ bucket تخزين باسم `attachments` (خاص، غير عام) لحفظ مرفقات المصاريف والتحويلات (صور/PDF).
   - **إذا كنت شغّلت نسخة أقدم من هذا الملف سابقًا:** يكفي تشغيل الجزء الأخير منه فقط (سطر `insert into storage.buckets ...`) لإضافة bucket المرفقات دون التأثير على بياناتك الحالية.
3. **إذا كانت قاعدة بياناتك تحتوي بيانات ومستخدمين بالفعل من نسخة سابقة**، شغّل أيضًا `security-migration.sql` كاملاً (نفس الطريقة: SQL Editor → Run). هذا يشفّر أي كلمات مرور مخزَّنة كنص صريح ولا يحذف أي بيانات — آمن للتشغيل أكثر من مرة.

من **Project Settings → API** انسخ:

- **مفتاح service_role السرّي** — في النظام الجديد اسمه غالبًا `SUPABASE_SECRET_KEY` (يبدأ بـ `sb_secret_...`)، وفي النظام القديم اسمه `service_role` (يبدأ بـ `eyJ...`).

⚠️ **هذا المفتاح لا يوضع أبدًا داخل `index.html` أو أي كود يُرسل للمتصفح** — فقط في متغيرات بيئة Render (الخطوة التالية).

### 5) النشر على Render كـ Web Service

1. **New + → Web Service** → اربط المستودع.
2. الإعدادات:

| الحقل | القيمة |
|---|---|
| **Language** | Node |
| **Build Command** | `npm install` |
| **Start Command** | `node server.js` |

3. **هذه هي الخطوة المهمة** — في قسم **Environment Variables** أضف ثلاثة متغيرات:

| Name | Value |
|---|---|
| `SUPABASE_URL` | `https://xxxxx.supabase.co` (رابط مشروعك) |
| `SUPABASE_SERVICE_KEY` | مفتاح service_role السرّي (من الخطوة 3 أعلاه) |
| `SESSION_SECRET` | نص عشوائي طويل وسرّي (32 حرفًا فأكثر) — يُستخدم لتوقيع جلسات الدخول. **لا تشاركه مع أحد.** يمكنك توليد واحد بأمر `openssl rand -hex 32` في أي طرفية، أو أي مولّد كلمات مرور عشوائية طويلة. |

⚠️ إذا لم تضِف `SESSION_SECRET`، سيعمل التطبيق لكن بمفتاح مؤقت يتغيّر مع كل إعادة تشغيل للخادم — مما يعني تسجيل خروج كل المستخدمين تلقائيًا عند كل نشر جديد أو إعادة تشغيل.

3.1 **لتفعيل ميزة "نسيت كلمة المرور"** (ترسل رمز تحقق بالبريد الإلكتروني المسجَّل)، أضف إحدى الطرق التالية:

⚠️ Render (وكثير من مزوّدي الاستضافة) تحجب منافذ SMTP الصادرة (587/465) افتراضيًا، فلو استخدمت SMTP التقليدي قد يعلّق زر "نسيت كلمة المرور" طويلًا ثم يفشل. الطريقتان أدناه (Resend وBrevo) ترسلان عبر HTTPS العادي (نفس بروتوكول فتح أي موقع) فلا تتأثران بهذا الحجب — جرّب إحداهما، ولو واحدة ما اشتغلت لأي سبب (حساب معلّق، نطاق غير موثّق...) جرّب الأخرى مباشرة بدون تعديل أي كود.

**الخيار 1 — Resend:**

1. أنشئ حساب مجاني على [resend.com](https://resend.com) (حتى 3000 إيميل/شهر مجانًا).
2. من **API Keys**، أنشئ مفتاحًا جديدًا.
3. للاختبار السريع فقط (يرسل فقط إلى بريدك الشخصي المسجَّل بحساب Resend نفسه): لا تضِف `RESEND_FROM` — سيُستخدم `onboarding@resend.dev` تلقائيًا.
   للاستخدام الفعلي مع كل المستخدمين: وثّق نطاقك (Domain) من **Domains → Add Domain** واتبع تعليمات سجلات DNS، ثم استخدم بريدًا من نفس النطاق كـ `RESEND_FROM`.
4. أضف في Render → Environment:

| Name | Value |
|---|---|
| `RESEND_API_KEY` | مفتاح الـ API الذي أنشأته |
| `RESEND_FROM` | بريد من نطاقك الموثّق (أو اتركه فارغًا للاختبار عبر `onboarding@resend.dev`) |

**الخيار 2 — Brevo:**

1. أنشئ حساب مجاني على [brevo.com](https://www.brevo.com) (حتى 300 إيميل/يوم مجانًا).
2. من **Settings → SMTP & API → API Keys**، ولّد مفتاح API جديد.
3. من **Senders & IP → Senders**، أضف ووثّق بريدك الإلكتروني كمُرسل (أسهل من توثيق نطاق كامل).
4. أضف في Render → Environment:

| Name | Value |
|---|---|
| `BREVO_API_KEY` | مفتاح الـ API الذي ولّدته |
| `SMTP_FROM` | البريد الإلكتروني الذي وثّقته كمُرسل في Brevo |

**الخيار 3 — SendGrid (بديل إن تعذّر الوصول لـ Resend أو Brevo):**

1. أنشئ حساب مجاني على [sendgrid.com](https://sendgrid.com) (حتى 100 إيميل/يوم مجانًا).
2. من **Settings → Sender Authentication → Single Sender Verification**، أضف ووثّق بريدك الإلكتروني كمُرسل (نفس مبدأ Brevo، بريد واحد فقط).
3. من **Settings → API Keys**، أنشئ مفتاحًا جديدًا (صلاحية Full Access أو Mail Send على الأقل).
4. أضف في Render → Environment:

| Name | Value |
|---|---|
| `SENDGRID_API_KEY` | مفتاح الـ API الذي أنشأته |
| `SENDGRID_FROM` | البريد الإلكتروني الذي وثّقته كمُرسل في SendGrid |

**الخيار 4 (بديل، غالبًا لا يعمل على Render) — SMTP تقليدي:**

| Name | Value |
|---|---|
| `SMTP_HOST` | مثل `smtp.gmail.com` أو مضيف مزوّد البريد الذي تستخدمه |
| `SMTP_PORT` | عادة `587` (أو `465` مع `SMTP_SECURE=true`) |
| `SMTP_USER` | اسم المستخدم/البريد الخاص بحساب الإرسال |
| `SMTP_PASS` | كلمة المرور أو مفتاح API الخاص بحساب الإرسال |
| `SMTP_FROM` | (اختياري) عنوان "المرسل" الظاهر — إن لم تضِفه يُستخدم `SMTP_USER` |
| `SMTP_SECURE` | (اختياري) اكتب `true` فقط إذا كان المنفذ `465` |

ترتيب الأولوية عند توفر أكثر من طريقة معًا: `RESEND_API_KEY` أولاً، ثم `BREVO_API_KEY`، ثم `SENDGRID_API_KEY`، ثم SMTP. بدون أي منها، زر "نسيت كلمة المرور" سيظهر خطأً واضحًا للمستخدم بدل التوقف بصمت — والميزة تتطلب أن يكون لكل مستخدم بريد إلكتروني صحيح مسجَّل في حسابه (عمود `email`).

4. **Create Web Service**. بعد انتهاء البناء يصبح التطبيق متاحًا على رابط مثل:
   `https://petty-cash.onrender.com`

### 6) أول تسجيل دخول
لا يوجد مستخدمون في قاعدة بيانات جديدة، لذلك يجب إنشاء أول حساب (رئيس اتحاد) يدويًا عبر **SQL Editor** — وليس Table Editor، حتى تُشفَّر كلمة المرور من البداية:

```sql
insert into users (user_id, federation_id, user_status, employee_name_ar, user_name, password, user_type)
values ('u_001', 'fed_001', 'مفتوح', 'اسمك هنا', 'admin', crypt('اختر-كلمة-مرور-قوية', gen_salt('bf')), 'رئيس الاتحاد');
```

سجّل الدخول بـ`admin` وكلمة المرور التي اخترتها، أنشئ بقية المستخدمين من داخل التطبيق (كلمات مرورهم تُشفَّر تلقائيًا)، وغيّر كلمة مرورك فورًا من "ملفي الشخصي" إذا أردت.

## الأمان

- **المتصفح لا يملك أي بيانات اتصال بقاعدة البيانات إطلاقًا** — فقط رابط موقعك. قاعدة البيانات مقفلة بالكامل أمام أي وصول مباشر من الإنترنت (RLS بلا سياسات anon)، والوصول الوحيد هو عبر خادمك على Render بمفتاح service_role.
- **كل عملية على `/api/db` (عدا تسجيل الدخول) تتطلب رمز جلسة صالح** صادر فقط بعد تسجيل دخول ناجح، ويُتحقَّق من صلاحية الحساب (نشط/معطّل، نوعه) من قاعدة البيانات في كل طلب — وليس فقط في لحظة الدخول. أي طلب مباشر للخادم (متجاوزًا الواجهة) بدون رمز صالح يُرفض تلقائيًا.
- **عزل بيانات الاتحادات:** كل قراءة وكتابة على الجداول المرتبطة باتحاد (العهد، المستخدمون، مراكز التكلفة، الرحلات، إلخ) تُقيَّد تلقائيًا على مستوى الخادم باتحاد المستخدم المسجّل دخوله — لا يقدر أي مستخدم يقرأ أو يعدّل بيانات اتحاد غيره حتى لو عرف معرّفات السجلات مباشرة (المراجع فقط يرى كل الاتحادات، كما هو مصمَّم في الواجهة).
- **كلمات المرور مشفّرة دائمًا** (bcrypt عبر امتداد pgcrypto في Postgres) — لا تُخزَّن ولا تُعرض كنص صريح في أي مكان، ولا تُقرأ عبر `/api/db` إطلاقًا (القراءة فقط عبر عرض `users_public` الذي لا يحتوي هذا العمود).
- **تحديد معدّل تسجيل الدخول:** محاولات الدخول من نفس العنوان مُقيَّدة بعدد محدَّد خلال فترة زمنية لمنع التخمين الآلي لكلمات المرور.
- **حماية إضافية على مستوى الخادم:** الحقول القابلة للإدخال/التعديل محصورة بقائمة معروفة لكل جدول (لا يمكن إرسال أعمدة غير متوقعة)، ولا يمكن لأي عميل تزييف مُنشئ السجل (`created_by`) أو نقل سجل لاتحاد آخر عبر التعديل.
- **إجراءات الاعتماد محمية بالكامل من الخادم:** كل عملية اعتماد/رفض/إقفال/تغيير صلاحية (عهدة، ميزانية، تحويل، مصروف، رحلة، مشارك، مستخدم) لها نقطة نهاية مخصّصة (`/api/action`) تعيد التحقق الكامل من الدور والصلاحية — بما في ذلك قواعد تعارض المصالح (مثل: عهدة رئيس الاتحاد يعتمدها المدير التنفيذي حصرًا) ومنع الاعتماد الذاتي — مباشرة من قاعدة البيانات، وليس فقط من الواجهة. أي محاولة تلاعب بطلب HTTP مباشر (تجاوز الواجهة) تُرفض بنفس القواعد تمامًا.
- **سجل تدقيق (Audit Log):** كل محاولة إجراء حسّاس تُسجَّل تلقائيًا بجدول `audit_log` — من قام بها، هل نجحت أو فشلت ولماذا، والوقت — سواء كانت محاولة مشروعة أو محاولة تلاعب مرفوضة.

⚠️ **ملاحظة محدَّثة:** الفجوة المذكورة سابقًا (الاعتماد على الواجهة فقط للصلاحيات الدقيقة) أُغلقت الآن بالكامل — كل إجراءات الاعتماد تمر عبر تحقق صلاحية حقيقي على الخادم. ما تبقّى خارج هذا النطاق هو عمليات القراءة/الإضافة/التعديل العامة غير الحسّاسة (مثل تعديل بيانات عهدة قيد الإعداد، إضافة مصروف جديد قبل اعتماده) والتي تبقى تعتمد على تحقق الحقول والاتحاد فقط دون تحقق دور دقيق — وهذا مقبول لأنها لا تمنح صلاحية مالية مباشرة (الاعتماد نفسه محمي).

### مراجعة سجل التدقيق
لعرض آخر المحاولات (ناجحة وفاشلة)، افتح **Supabase → SQL Editor** وشغّل:
```sql
select created_at, user_name, action, success, target_table, target_id, message
from audit_log
order by created_at desc
limit 100;
```
أو لعرض المحاولات الفاشلة فقط (قد تكشف محاولات تلاعب):
```sql
select created_at, user_name, action, message from audit_log where success = false order by created_at desc;
```

## هيكل قاعدة البيانات (ملخص)

- `federations` — الاتحادات
- `users` — المستخدمون (مراجع / رئيس اتحاد / مدير تنفيذي / محاسب / موظف / موارد بشرية / رئيس مجلس الادارة / عضو مجلس الادارة / لاعب / مرافق لاعب / حكم / متعاون)
- `cost_centers` — مراكز التكلفة (7 رئيسية ثابتة لكل اتحاد + فرعية)
- `expense_types` — أنواع المصاريف (موحّدة لكل الاتحادات)
- `custodies` — طلبات/سجلات العهد النقدية
- `custody_budgets` — المصاريف التقديرية لكل عهدة
- `custody_transfers` — التحويلات إلى كل عهدة
- `custody_closures` — المصاريف الفعلية لكل عهدة

راجع `schema.sql` للتفاصيل الكاملة لكل عمود.


## تحديث: الصلاحيات الجديدة وقواعد التعديل (v3)

شغّل `migration-roles-v3.sql` مرة واحدة على قاعدة بياناتك الحالية قبل استخدام هذه المزايا.

### 1) نوعان جديدان من المستخدمين
| النوع | السلوك |
|---|---|
| `رئيس مجلس الادارة` | صلاحياته **مطابقة تمامًا** لعضو مجلس الإدارة: يرى كل شيء، لا يعتمد ولا يوافق على شيء، لا يضيف مستخدمين، وعهدته الخاصة به فقط. |
| `مرافق لاعب` | معاملته **مطابقة تمامًا** للاعب: سجل داخل النظام فقط، **لا يستطيع تسجيل الدخول إطلاقًا** (الرفض على مستوى الخادم لا الواجهة فقط)، وبدله اليومي بفئة "لاعب". |

عند اختيار النوع `رئيس مجلس الادارة` في نافذة **إضافة/تعديل مستخدم** يظهر تلقائيًا زر تفعيل:
**«هل الرئيس عضو في اتحاد قاري؟» (نعم / لا)** — يُحفظ في عمود `is_continental_member`، ويظهر في صفحة تفاصيل المستخدم، ويختفي (ويُصفَّر على الخادم) لأي نوع آخر.

### 2) الأنواع المحمية — لا يعدّلها إلا مراجع اللجنة
الأنواع: **رئيس الاتحاد، المدير التنفيذي، رئيس مجلس الادارة، عضو مجلس الادارة**.

- لا يعدّل بياناتهم — ومنها **المسمى الوظيفي** ونوع المستخدم — إلا **مراجع اللجنة**، وله ذلك في أي وقت مهما كانت حالة الحساب.
- لا يجعل حساباتهم **"مفتوح"** (أو يغيّر حالتها أصلاً) إلا **مراجع اللجنة** — حتى رئيس الاتحاد والمدير التنفيذي ممنوعان.
- لا يستطيع أحد ترقية مستخدم عادي إلى أحد هذه الأنواع إلا مراجع اللجنة (الأنواع لا تظهر أصلاً في قائمة التعديل لغيره).
- **التحقق مكرَّر على الخادم** (`/api/action` و`/api/db`) وليس على الواجهة فقط، فأي طلب HTTP مباشر يتجاوز الواجهة يُرفض بنفس القواعد.

### 3) المهمة أو الدور لكل مشارك في الرحلة
حقل **إلزامي** جديد (`role_task`) في نافذة إضافة المشارك بنظام الانتدابات — لا يُحفظ المشارك بدونه. يظهر في:
جدول المشاركين بصفحة الرحلة · نافذة تفاصيل المشارك · قائمة المشاركين بمسودة الرحلة الجديدة · **طباعة تفاصيل الرحلة** · **طباعة قرار التكليف**.

### 4) فلتر العام
- الفترة الافتراضية صارت **السنة الميلادية الحالية كاملة: من 1/1 إلى 31/12** — وليست "سنة رجوعًا من تاريخ اليوم".
- أُضيفت قائمة **العام** المنسدلة أعلى الشاشة؛ اختيار أي سنة يضبط الفترة على 1/1 → 31/12 لتلك السنة ثم يزامن تلقائيًا.
- كل أرقام الفلتر (السنة والتواريخ) تُعرض بالأرقام **الإنجليزية اللاتينية** دائمًا.
- زر «آخر سنة» صار «السنة الحالية».


## تحديث: مدير اللجنة وضوابط سفر مجلس الإدارة (v4)

شغّل `migration-roles-v4.sql` مرة واحدة **بعد** `migration-roles-v3.sql`.

### 1) صلاحية جديدة: `مدير اللجنة`
- نطاق رؤيته كل الاتحادات (نفس نطاق مراجع اللجنة).
- **هو وحده من يضيف حسابات المراجعين** (ونوع «مدير اللجنة» نفسه) — النوعان لا يظهران أصلاً في قائمة نوع المستخدم لغيره، والتحقق مكرَّر على الخادم.
- **هو وحده من يعتمد سفر مجلس الإدارة المتجاوز للضوابط** (انظر البند 3).
- يقدر يعتمد/يرفض مشاركي أي اتحاد، ويشمله ما يشمل المراجع من صلاحيات تعديل الأنواع القيادية وتفعيل حساباتها.

### 2) سؤال «عضو في اتحاد قاري؟»
صار يظهر لـ **رئيس مجلس الإدارة وأعضاء مجلس الإدارة** معًا (كان لرئيس المجلس فقط)، ويؤثر مباشرة على ضوابط السفر أدناه.

### 3) ضوابط سفر رئيس وأعضاء مجلس الإدارة
السنة المعتمدة هي السنة الميلادية (1/1 → 31/12) حسب تاريخ بداية الرحلة.

**رئيس مجلس الإدارة:**

| الضابط | غير عضو في اتحاد قاري | عضو في اتحاد قاري |
|---|---|---|
| أيام الرحلة الواحدة | 9 أيام | 9 أيام |
| إجمالي أيام السفر سنويًا | 30 يومًا | 40 يومًا |
| عدد الرحلات سنويًا | 4 رحلات | 6 رحلات |

**عضو مجلس الإدارة:**
- داخل المملكة: **رحلتان فقط سنويًا** — واحدة لحضور **بطولة** وواحدة لحضور **معسكر**. أي نوع رحلة آخر داخل المملكة يُعدّ تجاوزًا.
- خارج المملكة: ممنوع، **إلا** إذا كان عضوًا في اتحاد قاري فله **رحلتان إضافيتان** خارج المملكة، و**تُخصمان من رصيد رحلات رئيس مجلس الإدارة** السنوي.

**السلوك عند التجاوز:** المشارك **لا يُمنع من الإدراج** ضمن الرحلة، بل يُدرج وعليه علامة وملاحظة توضّح السبب:

| العلامة | المعنى | أثرها |
|---|---|---|
| 🔴 **أحمر** (`تجاوز`) | تجاوز الضوابط | يُدرج ضمن المشاركين، ولا يعتمد سفره إلا **مدير اللجنة**. اعتماد قرار التكليف من رئيس الاتحاد/المدير التنفيذي لا يمرّره. |
| 🟡 **أصفر** (`عند الحد`) | بلغ حدّه ووقف عنده | يُدرج ويُعتمد بالمسار العادي، مع تنبيه. |

العلامة تظهر: في نموذج إضافة المشارك مباشرة عند اختياره · في جدول المشاركين بصفحة الرحلة · في نافذة تفاصيل المشارك · وتلوين اسم المستخدم في **قائمة المستخدمين** وصفحة تفاصيله حسب استهلاكه السنوي.

⚠️ **الخادم يعيد حساب العلامة بنفسه** عند حفظ كل مشارك ولا يثق بما ترسله الواجهة، فلا يمكن تزييف «ضمن الضوابط» لتفادي اشتراط اعتماد مدير اللجنة.


## تحديث: فلتر السنة وتحقق تواريخ الرحلات (v5 — لا يحتاج ترقية قاعدة بيانات)

### فلتر السنة في نظام الانتدابات
- أُلغي خيار **الفترة المخصصة** نهائيًا في `secondments.html`: الفترة دائمًا **سنة ميلادية كاملة** (1/1 → 31/12)، تُختار من قائمة **العام** فقط، والافتراضي السنة الحالية. مثال: عند اختيار 2026 تصبح الفترة `2026-01-01 ← 2026-12-31`.
- السبب: كل ضوابط سفر مجلس الإدارة (عدد الرحلات وعدد الأيام سنويًا) تُحسب على أساس السنة الميلادية — وأي فترة مخصصة كانت تعطي احتسابًا مضلِّلاً.
- أي فترة مخصصة محفوظة سابقًا في المتصفح تُطبَّع تلقائيًا إلى السنة الكاملة عند فتح البرنامج.
- تلوين المستخدمين بضوابط السفر (🔴/🟡) صار يتبع **السنة المختارة في الفلتر** لا سنة الجهاز.
- **ملاحظة:** فلتر نظام العهد النقدية (`index.html`) بقي كما هو — سنة كاملة افتراضيًا مع إمكانية تخصيص الفترة، لأن العهد لا تخضع لضوابط سنوية.

### تحقق تواريخ الرحلة
| القاعدة | السلوك |
|---|---|
| تاريخ بداية الرحلة **لا يسبق تاريخ اليوم** | حقل التاريخ نفسه لا يسمح باختياره (`min`)، ورسالة خطأ واضحة، ومنع الحفظ |
| تاريخ النهاية **لا يسبق تاريخ البداية** | نفس الشيء (تساوي التاريخين مسموح = رحلة ليوم واحد) |

- يسري على: **طلب رحلة جديدة**، **تعديل رحلة قائمة**، و**تواريخ المشارك** غير المطابق لتفاصيل الرحلة.
- زر «إضافة مشارك» في مسودة الرحلة يبقى معطّلاً حتى تصحّ التواريخ.
- عند تعديل رحلة قديمة، الإبقاء على تاريخ بدايتها الأصلي مسموح حتى لو كان ماضيًا (وإلا لتعذّر تعديل أي رحلة سابقة)، لكن أي تاريخ بداية **جديد** يخضع للشرط.
- **التحقق مكرَّر على الخادم** عند إضافة الرحلة وتعديلها، فلا يفيد تجاوز الواجهة.
